# CBS × DIS 統合: 要件定義（完成図）

状態: **一問一答で確定した内容（2026-11-12）。実装前。**
対象: Creative Brief Studio AI（CBS、`Htkym-yuic/creative-brief-studio-ai`）と DIS（本リポジトリ）の統合。
進め方: CBS 側にブランチ `feature/dis-integration` を切って作る（別リポジトリへの複製や、リポジトリの統合はしない）。`main` には直接書かない。

## 1. 完成図（ひとことで）
ヒアリングの結果から、DIS の事例（Section の流れ）をもとに、**3案（王道・個性・攻め）の構成案**を CBS が自動で作り、Section ごとの**型**から実装を生成して、**画面上のプレビューと提案書**まで出す。対象は、LP・Web・バナー・チラシ・ポスター・名刺などの複数媒体を、最初から見据えて設計する。

## 2. 確定した要件（一問一答の回答）
| # | 論点 | 決定 |
|---|---|---|
| Q1 | DIS の中心的な使われ方 | 構成案を自動で作る（添削・類似事例の提示は、あとで） |
| Q2 | 構成案の作り方 | 3案（王道＝複数事例の共通パターン、個性＝近い1事例の踏襲、攻め＝Section ごとの最適の組合せ） |
| Q3 | 事例選びの主な条件 | 最終目的（CV）、訴求・買う前の心理段階、価格帯・検討の重さ（業種は補助） |
| Q4 | 構成案の中身 | 並び＋各 Section の中身の指針＋コピー案＋パーツでカンプまで |
| Q5 | パーツの正体 | CBS が、構造から実装（既存の DOM/CSS モックアップ）を生成する。事例の画像は使わない（参考専用の権利を守る） |
| Q6 | 構造の表現 | 型（アーキタイプ）で分類する |
| Q7 | 型の一覧の決め方 | 既存事例（CBS の180件超＋DIS の Section）から集めて整理し、ユーザーが確定する |
| Q8 | 既存データとの関係 | 同じ LP に28章分析と DIS があるときは、内容で高い方を自動選択する（上書きはしない） |
| Q9 | 自動選択の基準 | 確信度と根拠の有無、Section 分解の精度 |
| Q10 | 最初の統合範囲 | 複数媒体を同時に設計する |
| Q11 | 共通の枠組み | 媒体ごとに別モデル（LP・Web は Section、バナー等は要素）。入口の画面だけ共通 |
| Q12 | CBS の流れへの組み込み | 既存の生成を DIS で補強する（事例選び・Section 順・パーツのところ） |
| Q13 | データの流し方 | CBS が書き出しを直接読む（コピーしない） |
| Q14 | 読む方法 | Dropbox の共有フォルダを読む |
| Q15 | CBS の動く場所 | 最初はローカル（Mac）、あとでクラウド。読み込み部分は差し替えやすくする |
| Q16 | カンプの出力 | 画面上のプレビューと提案書（ブラウザの印刷で PDF） |
| Q17 | 実装の最初の一歩 | Section の「型」の一覧づくり |

## 3. 全体の構成（案）
```
DIS（design-research-pipeline）                         CBS（ブランチ feature/dis-integration）
  分析（9軸・Section・型）                                 ヒアリング
        │                                                    │
        ▼                                                    ▼
  DIS 層の書き出し（dis-layer）                          事例選び（CV・心理段階・価格帯）
        │ Dropbox の共有フォルダ                               │
        └─────────────────────────────────────────────▶ 3案の構成案（王道・個性・攻め）
                                                              │
                                                              ▼
                                                    型 → 実装の生成 → プレビュー → 提案書
```
- 既存の CBS の参考事例（180件超、28章分析ベース）は変更しない。DIS の層は、参考事例の ID で結びつける「追加の層」として持つ。
- 同じ LP に両方があるとき、根拠は内容で自動選択する（Q8・Q9）。選択は読み込み時に行い、データは上書きしない。

## 4. DIS 側で足すもの
1. **Section の型（layoutArchetype）**: 分析の各 Unit に、型を付ける項目を足す（dis-2.x の分析スキーマの拡張）。型の一覧は、既存事例から集めて整理し、ユーザーが確定する（最初の一歩）。既存の分析（DIS の約13件）にも、あとから付ける。
2. **事例選びのための項目**: 最終目的（CV）、心理段階、価格帯・検討の重さを、事例ごとに構造化して持つ（今はタグや文章に散らばっている）。
3. **DIS 層の書き出し（dis-layer）**: ライブラリー番号ごとに、9軸の評価（根拠・確信度）、Section の一覧（種類・型・範囲・差し替え必須の要素・権利）、事例選びの項目を持つ。書き出し先は Dropbox の共有フォルダ。
4. **媒体ごとのモデル**: LP・Web は Section、バナー・チラシ・ポスター・名刺は要素（`docs/ANALYSIS_ITEMS_BY_MEDIA.md` を参照）。

## 5. CBS 側で足すもの（ブランチ）
1. DIS 層の型と読み込み（Dropbox のフォルダ）。ローカルの Mac では、同期済みのフォルダをそのまま読む。クラウドに出すときに、読み込み部分だけを差し替える。
2. 事例選び（CV・心理段階・価格帯・検討の重さ、業種は補助）。
3. 3案の生成（王道・個性・攻め）への DIS の補強。既存の生成は残し、事例選び・Section 順・パーツの所だけを補強する。
4. 型ごとの実装の生成（既存の LP カンプ画面を拡張）。
5. 根拠の表示（なぜこの事例か、なぜこの並びか）。
6. 28章と DIS が両方ある事例の、自動選択（確信度と根拠の有無、Section 分解の精度）。

## 6. 守る約束
- 既存の CBS の参考事例（181件）、Dropbox、Notion、既存の ID、ナレッジ、分析を、上書き・移動・削除しない。
- 事例の画像は、参考専用のまま。カンプに使わない（権利）。
- CBS の本流（`main`）には、確認なしに書かない。
- CBS への本番の反映は、ユーザーの確認後に行う。

## 7. 要確認・リスク（実装前に決める）
1. **Dropbox への書き出し**: DIS の書き出しを Dropbox に置くのは、新しい外部書き込み。方針（新規のみ、既存は上書きしない）と、置き場所（フォルダ名・ファイル名）を、ユーザーの確認後に決める。いまは本番の書き込みを止めている。
2. **下書きと採用済み**: CBS が直接読む方式（Q13）では、下書きのナレッジも見えてしまう。データ側に「採用済み／下書き」の状態を持たせ、読み込み側で扱いを決める（下書きは優先度を下げる、など）。
3. **Section 分解の自動選択（Q8・Q9）**: 28章側に、確信度・根拠の項目があるかを確認する（CBS の `sectionBreakdown` の中身を読む）。
4. **Next.js の注意**: CBS の指示書に、通常の Next.js と違う変更への注意がある。画面側の変更に入る前に、`node_modules` 内の資料を読む。
5. **媒体ごとの別モデル**: 最初の型の一覧づくりは LP・Web（Section）から始め、バナーなど（要素）は、並行して項目を決める。
6. **収集元の利用規約**: 自動収集に進む媒体は、規約の確認が前提（デザインAC、ロゴは保留）。

## 8. 実装の順序（案）
1. **型の一覧づくり**（最初の一歩）: CBS の180件超＋DIS の Section から型を集めて、案を作る。ユーザーが確定する。
2. 分析スキーマの拡張（型、CV・心理段階・価格帯の項目）と、既存の分析への型の付与。
3. DIS 層の書き出し（dis-layer）と、書き出し先・状態の方針の確定。
4. CBS ブランチ: 読み込み、事例選び、3案の補強、実装の生成、根拠の表示。
5. 媒体の拡張（Web、バナー、チラシ、ポスター、名刺）。
6. 添削（DIS の評価と添削チェックを使う）は、そのあと。
